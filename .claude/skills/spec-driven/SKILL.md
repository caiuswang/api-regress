# Spec Driven 开发流程

这个仓库的行为以 spec 为准（见 `CLAUDE.md` 的「文档体系」）。之所以先写 spec、再改代码，是因为用户要在动手之前 review 范围、决策和验收项；代码一旦先写了，review 就变成了追认，返工成本也高。所以整个流程分成两个阶段，中间隔着一道**用户确认**：

```
起草阶段（只动 doc/spec/）  ──用户明确同意──▶  实现阶段（才允许改代码）
```

## 什么时候需要新建 spec

| 情况 | 做法 |
|---|---|
| 新功能、行为变更、新命令/参数/配置字段、finding 类型、对比语义、报告或 `result.json` 格式变化 | 新建一个 spec 目录，走完整流程 |
| 已有 spec 范围内、还没实现完的需求有调整 | 改那个 spec（版本号 rN+1，新增或修改决策），同样等用户确认 |
| 代码没按已确认的 spec 实现（纯 bug，行为本该如此） | 不新建 spec；先说明打算怎么修，用户同意后再改 |
| 只改文档措辞、重构且行为不变 | 不需要 spec，但改代码之前仍然先说明并等用户点头 |

拿不准时按"需要 spec"处理，并告诉用户你的判断。

## 阶段一：起草 spec（不改代码）

### 1. 先读，再写

- `ls doc/spec/` 看已有的 spec 目录；读**最近一个** spec 的 `spec.md`（尤其是范围、决策记录）和 `tasks.md`，了解当前进度和已经否决过的方案。
- 读和需求相关的 `doc/user/`、`doc/dev/architecture.md`、`TODO.md`，以及相关代码。读代码、在 scratchpad 里做实测都可以——design.md 里"已实测"的结论正是这么来的。
- 和已确认的决策冲突时，不要自己推翻：在新 spec 的决策记录里列出来，标"待确认"，并在回复里点名提醒用户。

### 2. 建目录、取编号

- 目录：`doc/spec/v<N>-<slug>/`，N 是现有最大版本号 + 1，slug 是 2–4 个英文单词的短横线小写（如 `v3-har-import`）。
- 目录里固定三个文件：`spec.md`、`design.md`、`tasks.md`。
- **编号在每个 spec 内独立，从 1 开始**：任务 T1、T2…，决策 D1…，验收项 AC-01…，场景 S1…，限制 L1…，已知问题 K1…。不要接着上一个 spec 的编号往下排——多人同时在不同分支上写 spec 时，全局接续的编号会撞号，合并时还得重新编。
  - spec 内部直接写 `T2`、`D3`、`AC-05`。
  - 引用别的 spec 的编号时带上目录名，例如"v2-rules-tree 的 D27"，或链接 `[v2-rules-tree D27](../v2-rules-tree/spec.md)`。
  - v1-mvp、v2-rules-tree 是改规则之前写的，保持原来的全局编号（v2 从 D25、AC-38、T8 起），不要回头重编。

### 3. 按模板写三个文件

模板在 `references/`，写之前读对应的模板：

| 文件 | 模板 | 内容 |
|---|---|---|
| `spec.md` | `references/spec-template.md` | 行为规格：背景、范围（含"本期不做"）、行为定义、验收项、决策记录 |
| `design.md` | `references/design-template.md` | 实现约束：模块划分、关键约束、数据契约变化、依赖 |
| `tasks.md` | `references/tasks-template.md` | 任务拆分、依赖图、总览表、每个任务的交付/验收/review 重点/测试 |

格式上的几个要点（都沿用 v1、v2 的写法）：
- `spec.md` 是**增量的**：开头写明"基于上一版 spec，本文只写新增和改动的部分，没提到的行为一律沿用"。不要把旧 spec 抄一遍。
- 每个用户可见的行为都要落到一条可自动化验证的验收项上（"输入/操作 → 预期输出或退出码"），用表格。
- 决策记录写清楚**选了什么、为什么、否决了什么**（否决的方案和原因很重要，防止以后反复讨论）。你自己做的取舍一律标"待确认"，只有用户明确说过的才能写"已确认（日期）"。
- 文档里不写代码行号，写文件名或函数名。
- spec 内部可以互相引用（`§3`、`D27`、`../v2-rules-tree/spec.md`）；但 `doc/user/`、`doc/dev/`、代码、测试**不能**反过来引用 spec。

### 4. 拆 Task

每个 Task 结束时都要能独立跑测试、独立 review。按需求规模拆：

| 需求规模 | Task 数 |
|---|---|
| 简单（改一个模块、加一个参数） | 1–2 个 |
| 复杂（新命令、新数据格式、跨多个模块） | 4–6 个 |
| 拆完超过 6 个 | **先停下来问用户**：是接受这么多，还是拆成两个 spec、或合并任务 |

Task 太多意味着一次 review 的范围失控，所以超过 6 个时不要自作主张直接写进 tasks.md 当定稿——可以在 tasks.md 里写出草拟的拆分，但要在回复里明确请用户选择。

### 5. 停下来，请用户确认

写完三个文件后，**不要开始改代码**，也不要"顺手先把骨架搭起来"。回复里给出：
- 三个文件的路径；
- 一句话范围 + "本期不做"里最关键的几条；
- Task 列表（编号、一句话、依赖）；
- 所有"待确认"的决策，逐条列出，必要时给出你的推荐。

然后等用户回复。用户提出修改就改 spec（状态里的修订号 +1），再次请确认。

**什么算同意**：用户明确说"确认 / 可以 / 开始实现 / 按这个做"之类。用户只回答了某个问题、或者只说"不错"但还在讨论细节，不算开工许可；拿不准就问一句"可以开始实现 Tx 了吗？"。同意之后，把相关决策的状态改成"已确认（日期）"，spec 状态改成定稿。

## 阶段二：实现

### 分支

- 一个 spec 用**一个集成分支**：`feat/v<N>-<slug>`（和 spec 目录同名），从 `main` 拉出。这个 spec 的所有 Task 都在这个分支上做。
- **不要每个 Task 建一个分支**，除非用户主动要求。
- 第一次需要提交（提交 spec 或开始实现）时建分支；之前在别的分支上起草的 spec 文件一起带过去。

### 每个 Task

1. 开工前确认这个 Task 依赖的决策都已确认（tasks.md 里写了"开工前提"）。
2. tasks.md 总览表里的状态改成"进行中"。状态取值：未开始 / 进行中 / 待 review / 已完成。
3. 按交付清单实现，遵守 `CLAUDE.md` 的硬性约束、检查命令和「文档同步」表。
4. 实现中发现 spec 没覆盖或写错的地方：**行为相关的先停下来**，改 spec、新增决策（待确认），问用户后再继续；纯实现细节写进 design.md。
5. design.md 里已经落地的约束迁到 `doc/dev/`，原处留一句"已实现，见 doc/dev/…"。
6. 跑完 `radon cc -n C src/`、`lint-imports`、`pytest`，状态改成"待 review"，向用户汇报这个 Task 的结果和 review 重点，等用户 review。用户确认后改成"已完成"。
7. 提交只在用户要求时做。一个 Task 一个提交（spec 补充、代码、测试、文档放在一起），提交信息的 scope 带上版本号，因为 T1 在每个 spec 里都有：`feat(v<N>-t<编号>): <中文简述>`，例如 `feat(v3-t1): 解析 HAR 文件`；正文写为什么改、涉及的 AC 编号；和这个 Task 无关的改动单独提交。

一个 Task 完成后，不要自动开始下一个，除非用户说过"连续做完"。

### 全部完成

所有 Task 都是"已完成"后，告诉用户可以把集成分支合回 `main`（合并也要等用户要求）。

## 常见误区

- 起草阶段为了"验证可行性"直接改了 `src/` 或 `tests/`。验证请在 scratchpad 里做，结论写进 design.md。
- 起草阶段就更新了 `doc/user/`、`README.md`。这些描述的是**已实现**的行为，要在实现阶段对应的 Task 里改。
- 把自己的推荐写成"已确认"。
- 用户确认了 spec，就一口气做完所有 Task 且中间不停。
- 按 Task 建了 `feat/t11-xxx`、`feat/t12-xxx` 多个分支。
