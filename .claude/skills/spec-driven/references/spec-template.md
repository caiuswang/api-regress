# spec.md 模板

照这个结构写，章节可以按需求增删（行为定义部分通常拆成多个一级章节），但开头的状态块、范围、验收标准、决策记录必须有。尖括号里的内容替换掉。参照实例：`doc/spec/v2-rules-tree/spec.md`。

```markdown
# api-regress 产品需求 v<N>

> 状态：草案 r1（<YYYY-MM-DD>）
> 来源：<谁提出、什么问题，例如"用户反馈（2026-11-12）：……"；来自 TODO.md 的写"TODO.md 的 <条目>">
> 基于 [v<N-1> spec](../v<N-1>-<slug>/spec.md)：本文只写**新增和改动**的部分，没提到的行为一律沿用之前的 spec。
> 配套文档：实现约束见 [design.md](design.md)，任务拆分见 [tasks.md](tasks.md)。
> 决策记录见 §<X>。本 spec 的编号独立：决策从 D1、验收项从 AC-01、任务从 T1 开始；引用其他 spec 的编号时带目录名（如"v2-rules-tree 的 D27"）。
```

## 写法提醒

- 一条验收项只验证一件事的一组边界，能直接翻译成测试。
- 决策的状态只有两种：`待确认`、`已确认（YYYY-MM-DD）`。用户提出的写"（用户提出，日期）"。
- 已知限制有新增时加一节「已知限制与风险」，编号 L1 起，在本 spec 内独立。
- 修订时状态改成"草案 r2"，大的修订在状态行后面括号说明经过了几轮 review。
