# design.md 模板

design.md 写**实现时必须遵守的技术约束**和**实测过的结论**，不重复 spec 的行为描述。参照实例：`doc/spec/v2-rules-tree/design.md`、`doc/spec/v1-mvp/design.md`。

```markdown
# api-regress v<N> 技术设计约束

> 配套 [spec.md](spec.md)。之前版本的约束（[v<N-1> design](../v<N-1>-<slug>/design.md)、`doc/dev/`）全部继续有效，本文只写 v<N> 新增的部分。行为以 spec 为准，两者冲突时按 spec 执行。
> 实现完成后，相应内容迁移到 `doc/dev/`。

## 1. 模块划分

| 模块 | 职责 |
|---|---|
| `core/<x>.py`（新） | <职责；依赖谁、不能依赖谁> |
| `core/<y>.py` | <改动点> |

import-linter 契约：<不变 / 新增什么>。<文件接近 1000 行时说明怎么拆。>

## 2. 关键实现约束

- **<约束名>**：<怎么做、为什么；容易写成长 if 链的地方给出数据驱动的写法（有序规则表、分发表、max(key=...)）>
- **<已实测>**：<实测了什么、数据是多少、结论>

## 3. 数据契约变化

- `models.<X>`：<新增字段，默认值，对序列化的影响>
- `result.json`：<只增不删；是否需要重新导出 JSON Schema>
- 快照 / run 目录格式：<是否变化，版本号怎么处理>

## 4. 依赖

<不新增第三方依赖 / 新增 xxx（理由、版本）>
```

## 写法提醒

- 起草时可以在 scratchpad 里写脚本实测（性能、库的行为），结论写进来并注明"已实测"。不要为实测去改仓库里的代码。
- 实现阶段某项约束落地后，迁到 `doc/dev/`，这里留一句"已实现，迁到 `doc/dev/architecture.md` 的「…」一节"。
- 每个函数 CC ≤ 10、单文件 ≤ 1000 行，在模块划分时就要考虑。
